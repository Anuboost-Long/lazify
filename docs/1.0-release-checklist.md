# Lazify 1.0 — Release Checklist

Everything still standing between here and a 1.0 anyone can install.
Ordered by what blocks what, not by effort.

**Last updated:** 10 August 2026

**Where things stand:** macOS 1.0.0 is **published and installable**. The dist
repo is public, the release carries all five mac artifacts, and the one-line
installer has been run end to end against the live release. The source is
committed and pushed, and CI is green. What's left is Windows, the signing
certificates, and a website deploy.

## 🚩 Next up

- [ ] **Tag the source repo `v1.0.0`.** No tags exist yet. The tag must match
      `package.json` or the updater compares against the wrong version.

      ⚠️ **Order matters:** pushing a `v*` tag triggers `release.yml`, which
      publishes with `LAZIFY_DIST_TOKEN`. That secret does not exist yet
      (confirmed: the repo has no secrets), so tagging now gives you one red
      run. Either add the secret first, or expect that failure and ignore it —
      the macOS release is already published by hand and does not depend on it.

- [ ] **Add `LAZIFY_DIST_TOKEN` as a repository secret.** A fine-grained PAT
      with `contents: write` scoped to `lazify-dist` only, not to the source
      repo. `release.yml` already expects this exact name.

- [ ] **Deploy the website.** Everything below is written and building locally
      but not live: the two macOS download buttons, the install command, the
      macOS "damaged" card, and the Windows SmartScreen card. The footer's
      GitHub link also moved off the private source repo, which was a 404 for
      every visitor — that fix only helps once deployed.

- [ ] **Install on a genuinely clean Mac.** The verification above ran on this
      machine, into a scratch directory. A Mac that has never seen Lazify — and
      ideally an Intel one, which no one has tested — is the real check.

## 🔐 Trust & distribution

- [ ] **Apple Developer ID certificate ($99/yr) + notarization.**
      The highest-value item on this list. It removes the "damaged" dialog,
      removes the reason `install.sh` has to exist, **and unlocks in-app updates
      on macOS** — Squirrel.Mac validates the signature before applying an
      update, so mac auto-update cannot work until this lands. No code changes
      needed when it does; mac just starts working.

- [ ] **Windows code signing.** Azure Trusted Signing is far cheaper than a
      traditional OV cert. Removes the SmartScreen warning. Windows auto-update
      already works unsigned, so this is purely about the install funnel.

- [ ] **Add a LICENSE (or a deliberate "all rights reserved" note).** The dist
      README says Lazify is not open source, but the source repo has no license
      file at all. Decide commercial vs. open source — it's awkward to walk back.

## 🪟 Windows

- [ ] **Build and publish the Windows installer.** Nothing is missing but the
      run: it has to be built on Windows for node-pty's native module, which is
      what the `windows-latest` runner in `release.yml` is for. Artifacts are
      named `Lazify-Setup-${arch}.exe`.

- [ ] **Add the entry to `site.windowsDownloads` in `website/lib/site.ts`.**
      The card renders from that list and shows "Build in progress" while it is
      empty, so shipping is one entry and no code change.

- [ ] **Windows on ARM.** Decided: same treatment as macOS — a build per
      architecture with its own button, not one installer pretending to cover
      both. The website is already ready for it.

      What's left is the build. node-pty must be rebuilt against Electron per
      architecture, and cross-compiling for arm64 on an x64 runner is unproven.
      Both arches build in one electron-builder invocation, so a failure takes
      **x64 down with it** — add `arm64` to `electron-builder.win.yml` only
      after an x64 release is green, and watch that run.

- [ ] **Test Windows auto-update in place** — install 1.0.0, publish 1.0.1,
      confirm Settings → About → Updates downloads and restarts cleanly. This is
      the half of the updater that can actually be proven today.

## 🩺 Post-launch survivability

- [x] **Persistent logs.** Written to `app.getPath("logs")` —
      `~/Library/Logs/Lazify/lazify.log` on macOS — rotating at 2 MB with one
      generation kept. Synchronous writes, so the last line before a crash
      survives. The four `console.error` calls route through it and still print
      to the console. Verified: a packaged run creates the file and logs the
      startup line.

- [x] **Crash reporting.** Crashpad started with `uploadToServer: false`, so
      dumps collect locally and nothing leaves the machine. Uncaught
      exceptions, unhandled rejections, GPU/utility process deaths, and
      renderer crashes and hangs are all logged. Verified: the Crashpad
      database is created on launch.

- [x] **Bug reports go to the dist repo's Issues.** Settings → About →
      Diagnostics has "Report an issue", which opens a new issue prefilled with
      version, platform, arch and Electron version. One constant
      (`ISSUES_URL` in `DiagnosticsSection.tsx`) if you want to move it.

- [x] **Issues enabled on `lazify-dist`.** Confirmed via the API
      (`has_issues: true`), and the prefilled new-issue URL the button opens
      returns 200.

- [ ] **Decide what an uncaughtException should do.** Handling it means the app
      now survives what used to kill it, which is usually right but can leave it
      running in a broken state. If a fatal dialog and a clean quit would be
      better, that is a small change in `crash-handlers.ts`.

## 🧪 Worth a look, not blocking

- [ ] **`plugins: true` on the main window.** Added so the editor can render
      PDFs. In modern Chromium that is only the built-in PDF viewer, so the
      exposure is minimal — just know it is there.

- [ ] **Bundle size.** The renderer chunk is ~1.4 MB (379 KB gzipped) and Vite
      warns about it. Barely matters for a desktop app, but it is the easiest
      win if cold start ever feels slow.
