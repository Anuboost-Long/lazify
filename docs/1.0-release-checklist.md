# Lazify 1.0 — Release Checklist

Everything still standing between the current build and a 1.0 anyone can install.
Ordered by what blocks what, not by effort.

**Where things stand:** version is bumped to `1.0.0`, the mac DMG/ZIP for both
architectures are built and verified in `release/mac/`, the in-app updater is
wired end to end, and `lazify-dist` exists locally with its README and installer,
committed but not yet pushed.

---

## 🚩 Blocking — nothing ships until these are done

- [ ] **Create the public `Anuboost-Long/lazify-dist` repo on GitHub.**
      It must be public: the updater and `install.sh` both read release assets
      anonymously, and a private repo answers 404 to everyone without a token.

- [ ] **Push the dist repo.** It's committed and waiting at
      `/Users/administrator/Work/lazify-dist`:
      ```bash
      cd /Users/administrator/Work/lazify-dist
      git remote add origin https://github.com/Anuboost-Long/lazify-dist.git
      git push -u origin main
      ```

- [ ] **Publish the v1.0.0 release with all five mac artifacts.**
      `Lazify-arm64.dmg`, `Lazify-x64.dmg`, `Lazify-arm64.zip`, `Lazify-x64.zip`,
      and **`latest-mac.yml`**. The yml is not optional — without it the in-app
      updater has no feed to read. Don't upload the stale `0.1.0` files still
      sitting in `release/mac/` from August 5.

- [ ] **Tag the source repo `v1.0.0`.** The tag must match `package.json`, or the
      updater compares against the wrong version.

- [ ] **Verify the install path yourself on a clean Mac.**
      Run the one-liner, confirm it lands in `/Applications` and opens without
      the "damaged" dialog. This is the first thing every new user will do.

## 🔐 Trust & distribution

- [ ] **Apple Developer ID certificate ($99/yr) + notarization.**
      The single highest-value item after launch. It removes the "damaged"
      dialog, removes the need for `install.sh` to exist at all, **and unlocks
      in-app updates on macOS** — Squirrel.Mac validates the signature before
      applying an update, so mac auto-update simply cannot work until this lands.
      No code changes needed when it does; mac just starts working.

- [ ] **Windows code signing.** Azure Trusted Signing is far cheaper than a
      traditional OV cert. Removes the SmartScreen "unrecognised publisher"
      warning. Windows auto-update already works unsigned, so this is purely
      about the install funnel.

- [ ] **Add a LICENSE (or a deliberate "all rights reserved" note).**
      The dist README already says Lazify is not open source, but the source repo
      has no license file at all. Decide commercial vs. open source before 1.0 —
      it's awkward to walk back afterwards.

## ⚙️ CI & repeatability

- [ ] **Add `LAZIFY_DIST_TOKEN` as a repository secret.**
      A fine-grained PAT with `contents: write` scoped to `lazify-dist` only —
      not to the source repo. `release.yml` already expects this name.

- [ ] **Confirm the CI workflow runs green on a PR.** `ci.yml` typechecks both
      tsconfigs, runs the tests, and builds the renderer.

- [ ] **Do one full dry run of `release.yml`** on a throwaway tag before you
      trust it with a real one. The macOS runner builds thin arm64 + x64; the
      Windows runner compiles its own node-pty. This also fixes the current
      "only reproducible on my machine" problem.

## 🩺 Post-launch survivability

- [ ] **Persistent logs.** The four `console.error` calls in `src/main/` go
      nowhere once packaged. Write to `app.getPath("logs")` and add a "reveal
      logs" button in Settings — this turns "it doesn't work" into something you
      can actually debug, with none of the privacy questions telemetry raises.

- [ ] **Crash reporting.** `crashReporter` is never called. Even local crash
      dumps that a user can attach to an issue would be a step up from nothing.

- [ ] **Decide where bug reports go.** The dist repo's Issues tab is the obvious
      answer, and it's free — but decide before users go looking.

## 🧪 Worth a look, not blocking

- [ ] **`plugins: true` on the main window.** Added so the editor can render
      PDFs. In modern Chromium that's only the built-in PDF viewer, so the
      exposure is minimal — just know it's there.

- [ ] **Bundle size.** The renderer chunk is ~1.4 MB (379 KB gzipped) and Vite
      warns about it. Doesn't affect a desktop app's startup much, but it's the
      easiest win if cold start ever feels slow.

- [ ] **Windows on ARM.** Decided: treat it the way macOS is treated — a build
      per architecture with its own download button, not one installer
      pretending to cover both. The website side is already done; the Windows
      card renders from `site.windowsDownloads`, so shipping arm64 is a matter
      of adding an entry.

      What's left is the build itself. node-pty has to be rebuilt against
      Electron per architecture, and cross-compiling it for arm64 on an x64
      Windows runner is the unproven part. Adding `arm64` to
      `electron-builder.win.yml` fails the entire Windows job if it doesn't
      work — x64 included — so add it only once an x64 release is green, and
      watch that one CI run closely.
