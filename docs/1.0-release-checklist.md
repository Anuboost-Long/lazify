# Lazify 1.0 — Release Checklist

Everything still standing between here and a 1.0 anyone can install.
Ordered by what blocks what, not by effort.

**Last updated:** 10 August 2026

**Where things stand:** macOS 1.0.0 is **published and installable**. The dist
repo is public, the release carries all five mac artifacts, and the one-line
installer has been run end to end against the live release. The app now writes
logs, handles crashes, and can send a user to Issues with the build details
filled in. Source is pushed and CI is green on every commit. Housekeeping is
clear: the repo has a README and a LICENSE, the stash is gone, the stale build
artifacts are deleted, and no fabricated content ships on the site.

**What's left, in one line:** Windows, the two signing certificates, and a
website deploy. Everything blocking a macOS user is done.

**Eleven open items, and every one of them is blocked on something outside this
repo** — a payment, a Windows machine, a GitHub credential, or a second Mac.
Nothing is left that is merely unwritten:

| Blocked on | Items |
| --- | --- |
| Money | Apple Developer ID, Windows code signing |
| A Windows machine or runner | installer build, `windowsDownloads` entry, Windows on ARM, auto-update test |
| A GitHub credential | `LAZIFY_DIST_TOKEN`, the `v1.0.0` tag that needs it, the website deploy |
| Other hardware | clean-Mac install |
| A decision already made | screenshots — deliberately parked |

**Not verifiable from this machine:** `gh` is not installed here, so the absence
of `LAZIFY_DIST_TOKEN` and the CI runs after `e1fc7ca` are carried forward from
an earlier pass rather than re-checked. Everything else was verified against the
working tree, the network, or a local test run.

## 🔐 Trust & distribution

- [ ] **Apple Developer ID certificate ($99/yr) + notarization.**
      The highest-value item on this list. It removes the "damaged" dialog,
      removes the reason `install.sh` has to exist, **and unlocks in-app updates
      on macOS** — Squirrel.Mac validates the signature before applying an
      update, so mac auto-update cannot work until this lands. No code changes
      needed when it does; mac just starts working.

- [ ] **Windows code signing.** Azure Trusted Signing is far cheaper than a
      traditional OV cert. Removes the SmartScreen warning. Windows auto-update
      already works unsigned, so this is purely about the install funnel.

## 🪟 Windows

- [ ] **Build and publish the Windows installer.** Nothing is missing but the
      run: it has to be built on Windows for node-pty's native module, which is
      what the `windows-latest` runner in `release.yml` is for. Artifacts are
      named `Lazify-Setup-${arch}.exe`.

- [ ] **Add the entry to `site.windowsDownloads` in `website/lib/site.ts`.**
      The card renders from that list and shows "Build in progress" while it is
      empty, so shipping is one entry and no code change.

- [ ] **Windows on ARM.** Decided: same treatment as macOS — a build per
      architecture with its own button, not one installer pretending to cover
      both. The website is already ready for it.

      What's left is the build. node-pty must be rebuilt against Electron per
      architecture, and cross-compiling for arm64 on an x64 runner is unproven.
      Both arches build in one electron-builder invocation, so a failure takes
      **x64 down with it** — add `arm64` to `electron-builder.win.yml` only
      after an x64 release is green, and watch that run.

- [ ] **Test Windows auto-update in place** — install 1.0.0, publish 1.0.1,
      confirm Settings → About → Updates downloads and restarts cleanly. This is
      the half of the updater that can actually be proven today.

## 🩺 Post-launch survivability

- [x] **Persistent logs.** Written to `app.getPath("logs")` —
      `~/Library/Logs/Lazify/lazify.log` on macOS — rotating at 2 MB with one
      generation kept. Synchronous writes, so the last line before a crash
      survives. The four `console.error` calls route through it and still print
      to the console. Verified: a packaged run creates the file and logs the
      startup line.

- [x] **Crash reporting.** Crashpad started with `uploadToServer: false`, so
      dumps collect locally and nothing leaves the machine. Uncaught
      exceptions, unhandled rejections, GPU/utility process deaths, and
      renderer crashes and hangs are all logged. Verified: the Crashpad
      database is created on launch.

- [x] **Bug reports go to the dist repo's Issues.** Settings → About →
      Diagnostics has "Report an issue", which opens a new issue prefilled with
      version, platform, arch and Electron version. One constant
      (`ISSUES_URL` in `DiagnosticsSection.tsx`) if you want to move it.

- [x] **Issues enabled on `lazify-dist`.** Confirmed via the API
      (`has_issues: true`), and the prefilled new-issue URL the button opens
      returns 200.

- [x] **Decided: a fatal error closes the app cleanly.** An uncaught exception
      logs, shows "Lazify has to close" with the log path and a Show log button,
      then `app.quit()` so `will-quit` cleanup runs — with a 3s watchdog that
      forces the exit if a handler hangs. A crash before the app is ready skips
      the dialog and exits straight away. Unhandled rejections stay non-fatal:
      an unawaited fetch that rejects is not a corrupted process.

      A crashed **renderer** is offered a reload first, since that one really is
      recoverable, and only quits if the user says so.

- [x] **Flaky test fixed.** `command-runner-prompts.test.ts` was hitting
      vitest's 5s default (`Test timed out in 5000ms`), reproduced deterministically
      by running the suite under CPU load. It spawns a real process and talks to
      it over stdio, so its cost tracks how busy the machine is — ~1.5s idle,
      ~2.8s loaded, past 5s once vitest's own workers compete. Given 30s, along
      with `starter-provisioner.test.ts`, which shells out to real `git` for the
      same reason. Three suite runs under the load that previously failed twice
      now pass.

## 🧪 Looked at — no action needed

Both were "worth a look, not blocking". They have now been looked at, and the
answer in each case was to leave the code alone. Ticked as *reviewed*, not as
*changed* — nothing in this section altered a line of code.

- [x] **`plugins: true` on the main window.** Re-checked at `main.ts:324`.
      Verdict: leave it. NPAPI and PPAPI are both gone from modern Chromium, so
      the flag now toggles exactly one thing — the built-in PDF viewer — and
      `PdfPreview` renders through it, so removing the flag breaks PDF preview
      rather than hardening anything. The window it sits in keeps
      `contextIsolation: true`, `sandbox: true` and `nodeIntegration: false`,
      which is where the actual boundary is. `webviewTag: true` next to it is
      the more interesting line, and that one is already fenced to loopback by
      `guardPreviewWebviews`.

- [x] **Bundle size.** Re-measured today, and the recorded figure was right:
      the entry chunk is **1,389 kB / 381 KB gzipped**, which is what trips
      Vite's 500 kB warning.

      Worth knowing before anyone "fixes" it: that entry chunk is not the bulk
      of the build. `dist/assets` is **11 MB across 302 files**, nearly all of
      it Shiki language grammars — `emacs-lisp` alone is 780 kB, `cpp` 626 kB —
      and those are already split out and loaded on demand, which is the
      behaviour you want. So the warning points at the one chunk that is
      *hardest* to shrink and ignores the 9 MB that is already lazy. Still not
      worth acting on for a desktop app that loads from disk; revisit only if
      cold start ever feels slow, and measure before splitting.
